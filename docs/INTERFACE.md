# Contract interfaces

The JSON files in `docs/abi/` are full ABI arrays generated by `forge inspect` using
the pinned compiler. They include constructors, functions, errors and events.
All ids, amounts, periods and timestamps are `uint256`; ETH/token amounts use wei/minor
units. Both constructor argument arrays are empty, and both constructors are nonpayable.

## LaunchToken

| Function | Result / behavior |
| --- | --- |
| `name()` / `symbol()` | `Heartbeat` / `BEAT` |
| `decimals()` / `totalSupply()` | `18` / `10^27` |
| `balanceOf(account)` | Account's token balance |
| `allowance(owner, spender)` | Remaining approved amount |
| `transfer(to, value)` | Moves exactly `value`; returns `true` |
| `approve(spender, value)` | Replaces allowance; returns `true` |
| `transferFrom(from, to, value)` | Moves exactly `value` with caller allowance; returns `true` |

Zero transfers and self-transfers are supported. Zero transfer endpoints and zero
approval spenders are rejected. An allowance of `type(uint256).max` is never decremented.
Other allowances are decremented and emit `Approval` on spend; failed transfers revert
that change. Supply is minted only during construction via `Transfer(0, deployer, 10^27)`.
`Transfer(from, to, value)` indexes both addresses; `Approval(owner, spender, value)`
indexes both addresses. Custom errors use the `ERC20InvalidSender`,
`ERC20InvalidReceiver`, `ERC20InvalidApprover`, `ERC20InvalidSpender`,
`ERC20InsufficientBalance`, and `ERC20InsufficientAllowance` schemas in the ABI.

## DeadMansSwitch

The three constants are `MIN_PERIOD() = 86400`, `MAX_PERIOD() = 31536000` and
`RECOVERY_DELAY() = 31536000`. Let `D = lastPing + period` and `R = D + RECOVERY_DELAY`.

| Function | Caller / condition | Effect / return |
| --- | --- | --- |
| `create(address beneficiary, uint256 period)` payable | Any caller; valid period and beneficiary | Returns a new id, credits `msg.value` (including zero), starts clock |
| `ping(uint256 id)` | Depositor, open, timestamp `< D` | Resets clock |
| `deposit(uint256 id)` payable | Depositor, open, timestamp `< D`, value `> 0` | Credits that switch; resets clock |
| `withdraw(uint256 id, uint256 amount)` | Depositor, open, timestamp `< D`, `0 < amount <= balance` | Sends to depositor; resets clock |
| `setBeneficiary(uint256 id, address newBeneficiary)` | Depositor, open, timestamp `< D`; nonzero, not depositor | Replaces beneficiary; resets clock |
| `setPeriod(uint256 id, uint256 period)` | Depositor, open, timestamp `< D`; inclusive period bounds | Replaces period; resets clock using new period |
| `claim(uint256 id, address to)` | Current beneficiary, open, timestamp `>= D`, nonzero `to` | Zeroes balance, closes, pays whole balance to `to` |
| `reclaim(uint256 id, address to)` | Depositor, open, timestamp `>= R`, nonzero `to` | Zeroes balance, closes, pays whole balance to `to` |
| `switchInfo(uint256 id)` view | Existing id | Named tuple `(address depositor, address beneficiary, uint256 balance, uint256 period, uint256 lastPing, bool closed)` |
| `switchCount()` view | Any caller | Total ever created, including closed ids |
| `timeLeft(uint256 id)` view | Existing id | `max(D - block.timestamp, 0)`; zero after closure |

All functions except `create` and `deposit` reject attached ETH. Every mutation on a
closed id reverts; the read functions intentionally continue returning its history.
Invalid ids, including zero, revert on all per-id functions. All successful depositor
maintenance actions, including an unchanged beneficiary or period, reset `lastPing`.
The reentrancy lock covers all mutations; read calls remain available during callbacks.

## Events and client discovery

An asterisk marks an indexed field. Remaining fields are unindexed. All `id`, balance,
amount, period and timestamp fields are `uint256`; all party/recipient fields are addresses.

| Event | Fields in ABI order |
| --- | --- |
| `Created` | `id*`, `depositor*`, `beneficiary*`, `balance`, `period`, `lastPing` |
| `Pinged` | `id*`, `depositor*`, `lastPing` |
| `Deposited` | `id*`, `depositor*`, `amount`, `lastPing` |
| `Withdrawn` | `id*`, `depositor*`, `amount`, `lastPing` |
| `BeneficiaryChanged` | `id*`, `depositor*`, `newBeneficiary*` |
| `PeriodChanged` | `id*`, `depositor*`, `period`, `lastPing` |
| `Claimed` | `id*`, `beneficiary*`, `to`, `amount` |
| `Reclaimed` | `id*`, `depositor*`, `to`, `amount` |

From the published deployment block, query `Created` with the connected account as
depositor and separately as beneficiary, plus `BeneficiaryChanged` with the account as
`newBeneficiary`. Union and deduplicate the ids, then read `switchInfo` for each. Keep
only ids whose **current** depositor or beneficiary matches the account; a previous
beneficiary loses access even though historical logs still mention it. Use bounded RPC
block ranges and refresh on new blocks/account changes. `BeneficiaryChanged` deliberately
has the specified three-field schema; fetch the new clock from `switchInfo`.

Display time left from `timeLeft` and calculate recovery time from `switchInfo`.
Events support discovery, not authorization: the contract's current views and a fresh
transaction simulation determine which action can succeed. Handle reorgs and failed
transactions by refreshing state. Closed switches may be displayed as history.

## Application errors

| Error | Meaning |
| --- | --- |
| `UnknownSwitch(id)` / `ClosedSwitch(id)` | No switch at that id / mutation after settlement |
| `UnauthorizedDepositor()` / `UnauthorizedBeneficiary()` | Caller lacks the required per-switch role |
| `AlreadyLapsed()` / `NotLapsed()` | Depositor maintenance too late / beneficiary claim too early |
| `RecoveryNotAvailable()` | Recovery deadline has not arrived |
| `InvalidBeneficiary()` / `InvalidPeriod()` | Invalid beneficiary address / period outside bounds |
| `InvalidAmount()` | Zero deposit, zero withdrawal, or excessive withdrawal |
| `InvalidRecipient()` | Claim/reclaim destination is zero |
| `EtherTransferFailed()` | Recipient call failed; entire action and logs rolled back |
| `ReentrantCall()` | Mutation attempted while another mutation was executing |

A receiver can consume gas or reject payment; its failure affects only that transaction.
In particular, paying the switch contract itself fails because there is no receive or
fallback entry point. There is no automatic payout queue or iteration over recipients.
